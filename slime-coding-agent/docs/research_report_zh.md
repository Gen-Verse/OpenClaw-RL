# 可自我进化 Coding Agent 研究报告（基于 OpenClaw-RL + slime）

## 1. 问题定义

你要的不是“会写代码的模型”，而是“能在真实工程环境中持续提升的系统”：

- 能处理真实仓库与工具链；
- 能从失败中学习；
- 能在成本约束下提高成功率；
- 能把人工反馈转化为策略改进。

## 2. 关键研究结论（结合工程实践）

## 2.1 从静态 benchmark 走向 live workflow

传统 coding benchmark 提供离线单题评分，难覆盖：跨文件依赖、回归风险、团队规范、长期维护性。

**结论**：应以“真实任务流”作为主训练信号来源：issue、PR review、CI 失败、回滚事件。

## 2.2 强 agent 的核心不是单次生成，而是闭环控制

参考主流 coding agent 最佳实践，可靠性来自以下循环：

1. 任务拆解（Plan）
2. 最小改动实现（Edit）
3. 工具验证（Test/Lint/Build）
4. 失败归因与重试（Reflect）
5. 提交与总结（Commit/Report）

**结论**：训练目标应覆盖“过程质量”，而不只是最终答案。

## 2.3 自我进化依赖“高质量反馈面板”

仅靠 pass/fail 二值奖励会导致 reward hacking。建议构建多维反馈：

- 功能正确性：单测、集成测试；
- 工程质量：lint、复杂度、变更面大小；
- 安全稳定性：依赖安全、秘密扫描、回归率；
- 人工偏好：review 接受率、修改距离。

## 3. slime 适配价值

slime 的异步与解耦特性使其非常适合 coding 场景：

- rollout 可并行驱动多个沙盒任务；
- data buffer 可接入失败重放采样；
- trainer 与 judge 解耦，便于迭代奖励函数；
- 与 Megatron/SGLang 的组合支持规模化实验。

## 4. 推荐系统架构

## 4.1 五层架构

1. **入口层**：IDE/CLI/PR Bot。
2. **执行层**：容器沙盒 + 工具网关。
3. **评估层**：多评审器并行投票。
4. **训练层**：slime rollout + buffer + optimizer。
5. **进化层**：失败模式聚类 + 自动课程生成。

## 4.2 三角色策略（借鉴 coding agent workflow）

- **Planner**：生成步骤、风险点、验收条件。
- **Editor**：生成最小 patch。
- **Verifier**：决定继续修改、回滚、还是可提交。

优势：降低长任务漂移，提高工具使用纪律。

## 5. 奖励设计建议

```text
R_total = w_pass * R_pass
        + w_quality * R_quality
        + w_safety * R_safety
        + w_human * R_human
        - w_cost * R_cost
```

其中：

- `R_pass`: 测试通过与功能验收
- `R_quality`: 代码质量与变更约束
- `R_safety`: 安全扫描与回归惩罚
- `R_human`: 人工 review 偏好
- `R_cost`: token、时延、命令次数

## 6. 前沿论文与方法可借鉴点（工程抽象）

> 不追求逐篇“照搬算法”，而是提炼可落地机制。

1. **过程监督/结果监督结合**：过程轨迹奖励 + 最终验收奖励。
2. **自我反思与重试**：失败后基于错误类型选择不同策略（补测、回滚、重构）。
3. **工具增强推理**：先检索/执行再生成，减少幻觉。
4. **课程学习**：从简单修复到复杂跨模块任务逐步扩展。
5. **偏好对齐**：将 reviewer feedback 作为持续偏好信号。

## 7. 风险与防护

- **reward hacking**：仅优化能过测但不可维护的代码。
  - 防护：加入可维护性约束与回归惩罚。
- **过度修改**：为提通过率而进行大范围重写。
  - 防护：最小改动奖励与 diff budget。
- **工具误用**：命令过多、盲目重跑。
  - 防护：成本惩罚 + 命令策略学习。

## 8. 结论

建议先把“反馈协议 + 失败重放 + 多评审器”做扎实，再逐步上更复杂算法。对 coding agent 来说，**系统工程质量**往往比单点模型技巧更决定上限。
